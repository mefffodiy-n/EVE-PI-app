# EVE PI Manager — Roadmap (v2)

> Документ основан на анализе предыдущей реализации (репозиторий `mefffodiy-n/EVE-PI-app`,
> файлы `main.py`, `recipes.json`, `planet industry.csv`, `requirements.txt`, `readme.md`).
> Все константы (рецепты P1–P4, плотности сырья по планетам) переносятся из существующих
> файлов без изменений — они верны и переиспользуются как есть.

## 0. Принципы, обязательные для новой архитектуры

1. **ESI дергают только фоновые сборщики по расписанию.** Ни один пользовательский
   запрос (открытие страницы, расчёт плана, экспорт) не должен инициировать вызов ESI
   напрямую или косвенно (ни синхронно, ни "лениво при первом обращении").
2. **Минимум ESI-запросов в принципе:**
   - Type ID / SDE-справочники (имена P0–P4, id) — не запрашивать вообще при каждом
     старте; собрать один раз и закоммитить как статический JSON (как уже сделано для
     `recipes.json`), обновлять раз в релиз/раз в квартал через отдельный ручной скрипт,
     а не при запуске сервера.
   - Данные, которые вообще не требуют ESI (рецепты, плотности сырья по планетам,
     расчёт CPU/PG, дерево цепочек) — считать локально, как сейчас и делается в
     `recipes.json` + CSV.
   - Данные, которые обязаны идти через ESI (скиллы персонажа, статус колоний,
     таймеры экстракторов, OAuth) — только через отдельный worker с собственным
     расписанием и собственным rate-limit бюджетом, независимым от HTTP-запросов
     пользователей.
3. **Никакой имитации ESI-данных в проде.** Мок-персонажи (`Factory Chief`, `Miner N`)
   допустимы только в fixtures для тестов/дев-окружения, не в основном коде.
4. **Заглушки персонажей — легитимный инструмент отладки, но не часть auth-эндпоинта.**
   На момент разработки нет действующих ESI-токенов, и это нормально: логика
   планирования (`planner.py`, `capacity.py`) должна отлаживаться на тестовых
   персонажах независимо от того, готова ли ESI SSO. Требование — физически
   развести два пути:
   - боевой `/api/auth/callback` сразу пишется под реальный ESI OAuth (PKCE) и
     просто не будет работать, пока нет `client_id`/`client_secret` от
     developers.eveonline.com — это ожидаемо и не блокирует остальную разработку;
   - тестовые персонажи заводятся отдельным dev-only механизмом
     (`scripts/seed_dev_characters.py` или `POST /api/dev/seed-characters` под
     фиче-флагом `ENV=dev`), который пишет в ту же таблицу `characters`, что и
     реальный OAuth-flow, — благодаря этому `planner.py` не отличает, откуда взялся
     персонаж, и код не придётся переписывать, когда появятся настоящие токены.

## 1. Итоги аудита прошлой версии (кратко)

| Область | Проблема | Решение в v2 |
|---|---|---|
| ESI/Auth | `/api/auth/callback` не делает реальный OAuth-обмен, вставляет мок-персонажей | Полноценный ESI SSO flow (PKCE), токены только через фоновый refresh-worker |
| ESI/Auth | Тестовые персонажи вшиты прямо в боевой auth-роут — заглушку нельзя отключить, не переписывая эндпоинт | Заглушки выносятся в отдельный dev-only механизм (`scripts/seed_dev_characters.py`), не пересекающийся с боевым `/api/auth/callback` |
| ESI/частота | TypeID грузятся с ESI при каждом рестарте процесса | Статический `data/type_ids.json`, обновляется вручную/CI, не при старте |
| Токены | access/refresh хранятся в SQLite открытым текстом | Шифрование at rest (Fernet/libsodium), отдельная таблица `credentials` |
| Расчёты | CPU/PG — захардкоженные числа (95/85/75) | Реальная модель CPU/PG по типу Command Center и структурам |
| Расчёты | Штрафы на радиус планет заявлены, но не реализованы | Отдельный модуль `logistics/link_penalty.py` на основе `Radius [km]` из CSV |
| Данные | Рассинхрон имён (`Polyramids` vs `Polyaramids`) | Единый источник правды — нормализованный `recipes.json`, валидация при импорте CSV |
| Данные | Правая часть CSV (плотности для прямого R0→P2) не используется | Отдельный сценарий "прямое P2-производство" в планировщике |
| Инфраструктура | SQLite, без миграций, без multi-tenant | PostgreSQL + Alembic, per-user изоляция данных |
| Инфраструктура | Нет планировщика | APScheduler/Celery beat — единственная точка входа к ESI |
| Frontend | `web/index.html` — готовый SPA (751 строка), но FastAPI его не отдаёт: открывается как файл, отсюда хардкод `API_BASE='http://localhost:8000/api'` и вынужденный `CORS: *` | Смонтировать `web/` через `StaticFiles` — снимает и хардкод, и необходимость в `CORS: *` |
| Frontend | **Фиктивные таймеры экстракторов**: `index.html:475` дорисовывает `hours_left: Math.random()*22`, и это отрисовывается как настоящее время (красная пульсация при <2ч, сортировка «по времени таймера») | Поле `extractor_hours_left` приходит с бэкенда; `None` = «неизвестно» и так и показывается. Реальные данные — из `sync_colony_status` (Фаза 3) |
| Данные | `templates/*.json` (шаблоны застройки) не читает **ни бэкенд, ни фронтенд** — мёртвые данные, хотя readme обещал расчёт CPU/PG по ним | `domain/capacity.py::load_templates()` — первое место в проекте, где они реально используются |
| Данные | Шаблон `miner_p1.json` говорит «10 Basic Factories», а `main.py` считал `ceil(factories/12)` и писал «12 Basic Factories» | Зафиксировать одно значение (`BASIC_FACTORIES_PER_MINER_PLANET`), сверив с игрой |
| Данные | `Positron Cord` и `Ukomi Superconductors` в `recipes.json` имеют идентичные входы; `Positron Cord` отсутствовал в `PI_TYPE_NAMES` (нет type_id и цены) | Тест `test_no_duplicate_recipes_by_input_signature` падает намеренно, пока расхождение не разобрано |
| Логика | «Рекомендация» продукта = `max(цена за единицу)` по Jita buy, с ручным исключением Water/Oxygen — цена за единицу P4 несопоставима с P1, объём производства и затраты не учитываются | Считать ISK/час на цепочку, а не максимум цены |
| ESI/частота | Кнопка «SYNCING FUZZWORK» во фронте инициирует поход сервера на market.fuzzwork.co.uk (если кэшу >1ч) — пользовательское действие вызывает внешний запрос | `/api/market/best-product` только читает снапшот; наполняет его `refresh_market_prices` по расписанию |

## 2. Извлечённые константы (источник правды — без изменений)

- **Рецепты производства (P1→P4):** переносятся из `recipes.json` как есть — структура
  `{ "type": "P1|P2|P3|P4", "inputs": {...}, "source": "..." }` уже корректна и
  используется как основной справочник в новом модуле `domain/recipes.py`.
- **Плотности сырья по планетам региона:** переносятся из `planet industry.csv`
  (столбцы `Constellation; System; Planet; Type; Radius [km]; POCO Tax Rate [%];
  POCO Owner; <34 R0-ресурса>; <28 P2-ресурсов для прямого R0→P2>`).
  При импорте — обязательная нормализация заголовков (устранение опечаток
  `Polyramids→Polyaramids`, `Supertensil→Supertensile`) и валидация на дубликаты/`#REF`.
- **Шаблоны застройки планет:** переносятся из папки `templates/` прошлого репозитория
  в `data/templates/*.json`. Текущий формат минимален:
  `{"name": "...", "total_cpu": 12400, "total_pg": 16800}` — только суммарное
  потребление, без разбивки по структурам и без привязки к типу Command Center.
  Этого недостаточно для расчёта процентов загрузки (нет лимита), поэтому формат
  требует расширения — см. TODO в `domain/capacity.py`.
- Все три набора констант фиксируются как read-only seed-данные (миграция БД или
  версионируемый JSON), а не пересчитываются на лету из внешних источников.

## 4. Функциональные изменения относительно v1

- **Реальная ESI SSO авторизация** (PKCE) вместо мок-callback; после авторизации —
  персонаж и его refresh-token попадают в очередь фонового воркера, а не
  обрабатываются в HTTP-хендлере.
- **Синхронизация скиллов и колоний** — отдельные периодические джобы
  (`sync_character_skills`, `sync_colony_status`) с собственным интервалом (например,
  раз в 6–24 часа), independent от активности пользователей в UI.
- **Настоящий расчёт CPU/PG** по типу Command Center и структурам, а не константы.
- **Учёт штрафов по радиусу планеты** при выборе фабричного хаба (используя
  колонку `Radius [km]`, которая в v1 была прочитана, но не задействована).
- **Поддержка прямого сценария R0→P2** — вторая часть CSV-матрицы, которая в v1
  импортировалась, но никогда не использовалась.
- **Мультирегиональность** — CSV-импорт делается как отдельная фоновая задача с
  версионированием набора данных (регион/дата снапшота), а не единственный
  захардкоженный файл, тянущийся в память при старте.
- **Мультитенантность** — персонажи и планы привязаны к пользователю/аккаунту,
  а не к общей таблице `characters`.
- **Подключение существующего фронтенда** — `web/index.html` монтируется через
  `StaticFiles`, что убирает хардкод `API_BASE='http://localhost:8000/api'`
  и снимает необходимость в `CORS: *` (фронт станет same-origin).
- **Устранение фиктивных данных в UI** — убрать `Math.random()` из расчёта
  времени экстракторов; пока бэкенд не отдаёт реальное значение, показывать
  «неизвестно», а не правдоподобное число.
- **Задействование шаблонов застройки** — `data/templates/*.json` начинают
  реально влиять на расчёт CPU/PG (в v1 лежали без использования).

## 5. Технологический стек (предложение)

- **Backend**: FastAPI (оставляем — адекватный выбор), Pydantic v2.
- **БД**: PostgreSQL + SQLAlchemy 2.0 + Alembic (замена SQLite — нужна для
  multi-tenant и конкурентного доступа воркеров и API).
- **Планировщик**: APScheduler (если инфраструктура простая, один процесс) или
  Celery + Redis (если нужна отказоустойчивость/несколько воркеров) — в любом
  случае это единственная точка вызова ESI.
- **Кэш**: Redis для рыночных цен и справочников (замена `MARKET_CACHE` в памяти
  процесса — сейчас кэш теряется при каждом рестарте).
- **Frontend**: оставляем как есть — `web/index.html` это самодостаточный SPA
  (Tailwind через CDN, весь JS inline, без билд-шага). Переписывать не нужно;
  требуются только точечные правки: убрать `Math.random()`-таймеры и заменить
  хардкод `API_BASE` на относительный путь после монтирования статики.
  Сборщик/фреймворк не вводим — для одного файла это лишняя сложность.
- **Секреты**: `.env`/Vault, шифрование токенов в БД, `POCO Owner`/регион — конфиг,
  а не хардкод.
