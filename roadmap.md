# EVE PI Manager — Roadmap (v2)

> Документ основан на анализе предыдущей реализации (репозиторий `mefffodiy-n/EVE-PI-app`,
> файлы `main.py`, `recipes.json`, `planet industry.csv`, `requirements.txt`, `readme.md`).
> Все константы (рецепты P1–P4, плотности сырья по планетам) переносятся из существующих
> файлов без изменений — они верны и переиспользуются как есть.

## 0. Принципы, обязательные для новой архитектуры

1. **ESI дергают только фоновые сборщики по расписанию.** Ни один пользовательский
   запрос (открытие страницы, расчёт плана, экспорт) не должен инициировать вызов ESI
   напрямую или косвенно (ни синхронно, ни "лениво при первом обращении").
2. **Минимум ESI-запросов в принципе:**
   - Type ID / SDE-справочники (имена P0–P4, id) — не запрашивать вообще при каждом
     старте; собрать один раз и закоммитить как статический JSON (как уже сделано для
     `recipes.json`), обновлять раз в релиз/раз в квартал через отдельный ручной скрипт,
     а не при запуске сервера.
   - Данные, которые вообще не требуют ESI (рецепты, плотности сырья по планетам,
     расчёт CPU/PG, дерево цепочек) — считать локально, как сейчас и делается в
     `recipes.json` + CSV.
   - Данные, которые обязаны идти через ESI (скиллы персонажа, статус колоний,
     таймеры экстракторов) — только через фоновые сборщики по расписанию
     (`scripts/` + `scripts/scheduler.py`), независимо от HTTP-запросов
     пользователей. Единственное исключение — сам OAuth-flow: обмен кода на
     токен по природе синхронный, но разовый (см. `CLAUDE.md`, правило 3).
3. **Стек: Flask, без Docker.** FastAPI заменён на Flask; развёртывание —
   обычное WSGI-приложение (waitress на Windows, gunicorn на Linux) за nginx.
4. **Приложение не должно тяжело нагружать сервер при большом числе
   пользователей.** Flask синхронный, поэтому долгая работа в обработчике
   блокирует воркер целиком. Механизмы (реализованы в `api/cache.py`):
   справочники считаются один раз на процесс и отдаются с ETag (304 на
   повторный запрос — тело не формируется вовсе); расчёт плана кэшируется
   по параметрам и выполняется вне блокировки; жёсткие лимиты на размер
   запроса (20 продуктов на расчёт, 500 строк на экспорт); CSV читается
   и очищается однократно. Кэш — в памяти процесса; Redis вводить только
   после того, как нагрузка подтвердится измерением.
5. **Никакой имитации ESI-данных в проде.** Мок-персонажи (`Factory Chief`, `Miner N`)
   допустимы только в fixtures для тестов/дев-окружения, не в основном коде.
6. **Заглушки персонажей — легитимный инструмент отладки, но не часть auth-эндпоинта.**
   На момент разработки нет действующих ESI-токенов, и это нормально: логика
   планирования (`planner.py`, `capacity.py`) должна отлаживаться на тестовых
   персонажах независимо от того, готова ли ESI SSO. Требование — физически
   развести два пути:
   - боевой `/api/auth/callback` сразу пишется под реальный ESI OAuth (PKCE) и
     просто не будет работать, пока нет `client_id`/`client_secret` от
     developers.eveonline.com — это ожидаемо и не блокирует остальную разработку;
   - тестовые персонажи заводятся отдельным dev-only механизмом
     (`scripts/seed_dev_characters.py` или `POST /api/dev/seed-characters` под
     фиче-флагом `ENV=dev`), который пишет в ту же таблицу `characters`, что и
     реальный OAuth-flow, — благодаря этому `planner.py` не отличает, откуда взялся
     персонаж, и код не придётся переписывать, когда появятся настоящие токены.

7. **Справка и «О проекте» — часть поставки, а не приложение к ней.**
   Любое изменение функциональности, версии или данных сопровождается
   правкой этих разделов в том же заходе. Правило проверяется тестом
    по реестру : каждая заявленная
   возможность обязана быть описана на обоих языках.

## 1. Итоги аудита прошлой версии (кратко)

| Область | Проблема | Решение в v2 |
|---|---|---|
| ESI/Auth | `/api/auth/callback` не делает реальный OAuth-обмен, вставляет мок-персонажей | Полноценный ESI SSO flow (PKCE), токены только через фоновый refresh-worker |
| ESI/Auth | Тестовые персонажи вшиты прямо в боевой auth-роут — заглушку нельзя отключить, не переписывая эндпоинт | Заглушки выносятся в отдельный dev-only механизм (`scripts/seed_dev_characters.py`), не пересекающийся с боевым `/api/auth/callback` |
| ESI/частота | TypeID грузятся с ESI при каждом рестарте процесса | Статический `data/type_ids.json`, обновляется вручную/CI, не при старте |
| Токены | access/refresh хранятся в SQLite открытым текстом | Шифрование at rest (Fernet/libsodium), отдельная таблица `credentials` |
| Расчёты | CPU/PG — захардкоженные числа (95/85/75) | Реальная модель CPU/PG по типу Command Center и структурам |
| Расчёты | Штрафы на радиус планет заявлены, но не реализованы | Отдельный модуль `logistics/link_penalty.py` на основе `Radius [km]` из CSV |
| Данные | Рассинхрон имён (`Polyramids` vs `Polyaramids`) | Единый источник правды — нормализованный `recipes.json`, валидация при импорте CSV |
| Данные | Правая часть CSV (плотности для прямого R0→P2) не используется | Отдельный сценарий "прямое P2-производство" в планировщике |
| Инфраструктура | SQLite, без миграций, без multi-tenant | PostgreSQL + Alembic, per-user изоляция данных |
| Инфраструктура | Нет планировщика | APScheduler/Celery beat — единственная точка входа к ESI |
| Frontend | `web/index.html` — готовый SPA (751 строка), но FastAPI его не отдаёт: открывается как файл, отсюда хардкод `API_BASE='http://localhost:8000/api'` и вынужденный `CORS: *` | Смонтировать `web/` через `StaticFiles` — снимает и хардкод, и необходимость в `CORS: *` |
| Frontend | **Фиктивные таймеры экстракторов**: `index.html:475` дорисовывает `hours_left: Math.random()*22`, и это отрисовывается как настоящее время (красная пульсация при <2ч, сортировка «по времени таймера») | Поле `extractor_hours_left` приходит с бэкенда; `None` = «неизвестно» и так и показывается. Реальные данные — из `sync_colony_status` (Фаза 3) |
| Данные | `templates/*.json` (шаблоны застройки) не читает **ни бэкенд, ни фронтенд** — мёртвые данные, хотя readme обещал расчёт CPU/PG по ним | Каталог шаблонов в `data/pi_reference.json`, реально используется в `domain/capacity.py` |
| Данные | **Числа в `miner_p1.json` не соответствуют источнику**: заявлено `12400 CPU / 16800 PG` для «Miner + 10 Basic Factories». `12400` — это полный CPU шаблона P4 на 1 фабрику, `16800` — PG от 24 Advanced-фабрик. Два несвязанных числа из разных строк | Файл удалён. Реальный 00-шаблон майнера: 1 экстрактор (10 голов) + 8 basic-фабрик + storage + launchpad, 10 линков = **6100 CPU / 10400 PG** без голов и линков |
| Расчёты | Константы v1 (16 фабрик для P4, 24 для P2/P3) неявно предполагали Command Center Upgrades V у **всех** персонажей — это ровно варианты шаблонов «2 шаблона на планету». Значение 12 для P1 не соответствует ни одному шаблону (у 00 — 8 фабрик, у LS — 4) | Доступность вариантов проверяется явно через `available_templates_for(ccu, planet_type)` |
| Логика | «Рекомендация» продукта = `max(цена за единицу)` по Jita buy, с ручным исключением Water/Oxygen — цена за единицу P4 несопоставима с P1, объём производства и затраты не учитываются | Считать ISK/час на цепочку, а не максимум цены |
| ESI/частота | Кнопка «SYNCING FUZZWORK» во фронте инициирует поход сервера на market.fuzzwork.co.uk (если кэшу >1ч) — пользовательское действие вызывает внешний запрос | `/api/market/best-product` только читает снапшот; наполняет его `refresh_market_prices` по расписанию |

## 2. Извлечённые константы (источник правды — без изменений)

- **Рецепты производства (P1→P4):** переносятся из `recipes.json` как есть — структура
  `{ "type": "P1|P2|P3|P4", "inputs": {...}, "source": "..." }` уже корректна и
  используется как основной справочник в новом модуле `domain/recipes.py`.
- **Плотности сырья по планетам региона:** переносятся из `planet industry.csv`
  (столбцы `Constellation; System; Planet; Type; Radius [km]; POCO Tax Rate [%];
  POCO Owner; <34 R0-ресурса>; <28 P2-ресурсов для прямого R0→P2>`).
  При импорте — обязательная нормализация заголовков (устранение опечаток
  `Polyramids→Polyaramids`, `Supertensil→Supertensile`) и валидация на дубликаты/`#REF`.
- **Шаблоны застройки и характеристики структур:** источник —
  https://github.com/DalShooth/EVE_PI_Templates (README + разбор самих
  JSON-шаблонов; копии также на wiki.eveuniversity.org с разрешения автора).
  Выгружено в `data/pi_reference.json`:
  - ёмкость командного центра по уровням Command Center Upgrades (0–5):
    от `1675 CPU / 6000 PG` до `25415 CPU / 19000 PG`;
  - стоимость каждой структуры: ECU `400/2600`, basic-фабрика `200/800`,
    advanced `500/700`, high-tech `1100/400`, storage `500/700`,
    launchpad `3600/700`, голова экстрактора `110/550`;
  - **модель линков формулой**, а не таблицей: `L = 0.012·radius + 1`,
    затем `cpu = 15 + 0.2·L` и `pg = 10 + 0.15·L` на один линк.
    Формула воспроизводит все 60 точек 5 таблиц README с отклонением < 1
    и, в отличие от таблиц, работает при любом числе линков — это
    обязательно, потому что у 00-шаблона майнера 10 линков, а такой
    таблицы в README нет;
  - каталог шаблонов (**только варианты 00**, LS исключён решением проекта);
  - пропускная способность фабрик и рекомендованные уровни скиллов.

  Стоимости структур сходятся со строками README для вариантов на 1 фабрику
  точно (6 проверок). Набор шаблонов разобран полностью: 68 файлов
  (45 P2/P3, 8 P4, 15 майнеров 00), составы совпали с каталогом.

  **Два расхождения внутри источника**, оба зафиксированы в `_source`:
  1. Предупреждение про перегрузку майнера выше 15 000 км не сходится
     с таблицами README (расчёт даёт ~26 000 км для LS). На 00-вариант
     не влияет — там 10 голов, а не 16.
  2. README указывает `Starport 3600 CPU` для варианта на 1 фабрику,
     но `Starport x2 = 5200` для варианта на 2, хотя 2×3600 = 7200
     (по PG при этом сходится). Модель берёт консервативные 7200.
     **Цена вопроса велика**: для `p4_2factory` при CCU V предельный
     радиус планеты — 9 600 км против 61 700 км. Требует проверки в игре;
     управляется полем `assumptions.launchpad_count_for_two_templates`.

- **Сами JSON-шаблоны** разбираются модулем `domain/templates.py`:
  пины, линки, маршруты, схемы, число голов экстрактора. Это нужно не
  только для расчёта CPU/PG, но и чтобы подставить `CmdCtrLv` под уровень
  конкретного персонажа и отдать готовый файл для импорта в игру —
  README источника описывает эту правку как ручную операцию.

## 3. Предлагаемая структура приложения

> **Историческая заметка.** Диаграмма ниже — исходное предложение. По факту
> фоновые сборщики лежат плоско в `scripts/` (без `workers/jobs/`), `infra/`
> — это `config.py`/`db.py`/`models.py`/`crypto.py` (без вложенного `db/`),
> добавились `credentials.py`, `logging.py`, `esi_sso.py`, `serve.py`,
> `backup.py`, `sync_*`. Актуальное устройство — в `CLAUDE.md`, раздел
> «Устройство».

именно так их вызывает существующий `web/index.html`. Менять контракт без

## 4. Функциональные изменения относительно v1

- **Реальная ESI SSO авторизация** (PKCE) вместо мок-callback; после авторизации —
  персонаж и его refresh-token попадают в очередь фонового воркера, а не
  обрабатываются в HTTP-хендлере.
- **Синхронизация скиллов и колоний** — отдельные периодические джобы
  (`sync_character_skills`, `sync_colony_status`) с собственным интервалом (например,
  раз в 6–24 часа), independent от активности пользователей в UI.
- **Настоящий расчёт CPU/PG**: потребление = структуры шаблона + головы
  экстракторов + линки; лимит = ёмкость CC при данном уровне CCU.
- **Радиус планеты реально влияет на расчёт** — линки дорожают с радиусом,
  поэтому одна и та же застройка влезает на маленькую планету и не влезает
  на большую. В v1 колонка `Radius [km]` читалась из CSV и не использовалась.
- **Два шаблона на одну планету** (`p2p3_2factory` / `p4_2factory`) —
  доступны только при Command Center Upgrades V. Это вдвое сокращает число
  нужных планет, поэтому напрямую влияет на весь план и проверяется явно
  для каждого персонажа.
- **Ограничения по типу планеты**: P4-шаблоны — только Barren и Temperate.
- **Правило подбора площадок под переработку** (решение проекта, сужает
  источник — там P2/P3 разрешены на любом типе): вся переработка P2–P4
  идёт только на Barren и Temperate, планеты берутся **по возрастанию
  радиуса**, поскольку линки дорожают с размером.
- **Предупреждение вместо тихого отката.** Если в выбранной пользователем
  домашней системе планеты крупнее предела для двух шаблонов, планировщик
  не подставляет молча одиночный вариант, а сообщает: самая мелкая планета
  такая-то, предел такой-то, и предлагает выбрать — другая домашняя
  система или один шаблон на планету (вдвое больше планет и персонажей).
  Одиночный вариант применяется только по явному согласию
  (`allow_single_template_fallback`).
- **Генерация готовых шаблонов под персонажа**: подстановка `CmdCtrLv`
  в исходный JSON и выдача файла для импорта в игру.
- **Поддержка прямого сценария R0→P2** — вторая часть CSV-матрицы, которая в v1
  импортировалась, но никогда не использовалась.
- **Мультирегиональность** — CSV-импорт делается как отдельная фоновая задача с
  версионированием набора данных (регион/дата снапшота), а не единственный
  захардкоженный файл, тянущийся в память при старте.
- **Мультитенантность** — персонажи и планы привязаны к пользователю/аккаунту,
  а не к общей таблице `characters`.
- **Подключение существующего фронтенда** — `web/index.html` монтируется через
  `StaticFiles`, что убирает хардкод `API_BASE='http://localhost:8000/api'`
  и снимает необходимость в `CORS: *` (фронт станет same-origin).
- **Устранение фиктивных данных в UI** — убрать `Math.random()` из расчёта
  времени экстракторов; пока бэкенд не отдаёт реальное значение, показывать
  «неизвестно», а не правдоподобное число.
- **Задействование шаблонов застройки** — характеристики из
  `data/pi_reference.json` реально влияют на расчёт (в v1 шаблоны лежали
  в репозитории без использования, да ещё и с неверными числами).

## 5. Технологический стек (предложение)

- **Backend**: Flask (замена FastAPI по правилам проекта). Валидация тела
  запроса — вручную в `api/cache.py::parse_json_body`, без Pydantic:
  задача минимальна (не пустить мусор в domain), отдельная схема избыточна.
- **WSGI-сервер**: waitress (Windows, основная среда разработки) либо
  gunicorn (Linux). Docker не используется.
- **БД**: SQLAlchemy 2.0 + Alembic. На разработке — SQLite `data/pi_director.db`
  (реализовано, Фаза 3); в проде — PostgreSQL (нужен для multi-tenant и
  конкурентного доступа воркеров и API), переключение сменой `PI_DATABASE_URL`.
- **Планировщик**: APScheduler (если инфраструктура простая, один процесс) или
  Celery + Redis (если нужна отказоустойчивость/несколько воркеров) — в любом
  случае это единственная точка вызова ESI.
- **Кэш**: Redis для рыночных цен и справочников (замена `MARKET_CACHE` в памяти
  процесса — сейчас кэш теряется при каждом рестарте).
- **Frontend**: оставляем как есть — `web/index.html` это самодостаточный SPA
  (Tailwind через CDN, весь JS inline, без билд-шага). Переписывать не нужно;
  требуются только точечные правки: убрать `Math.random()`-таймеры и заменить
  хардкод `API_BASE` на относительный путь после монтирования статики.
  Сборщик/фреймворк не вводим — для одного файла это лишняя сложность.
- **Секреты**: `.env`/Vault, шифрование токенов в БД, `POCO Owner`/регион — конфиг,
  а не хардкод.
- **Кэш**: на Фазе 1 — в памяти процесса (`api/cache.py`), без внешних
  зависимостей. Redis вводится в Фазе 2 вместе с воркерами, когда
  появится необходимость делить снапшот цен между процессами.

      **Найдена и исправлена системная ошибка (11.09.2026, обнаружил
      пользователь: «ни одной работающей фабрики, хотя это не так»).**
      `last_cycle_start` у пина фабрики ESI пересчитывает НЕ в реальном
      времени, а только когда игрок открывает эту колонию в игровом
      клиенте (подтверждено сторонними источниками — esi-issues #654,
      форум разработчиков ESI). Фабрика в игре крутит циклы сама, пока
      есть сырьё, а поле у ESI «зависает» на последнем визите. Прежний
      расчёт («цикл по расчёту кончился → простаивает») делал вывод из
      устаревших данных как из свежих — почти все колонии, которые давно
      не открывали в игре, показывались простаивающими поголовно, хотя
      наверняка продолжали работать. Ровно то «правдоподобное, но ложное»
      число, которое запрещает правило 1.
      Исправлено (`pinCycleInfo()`, `structureUnitFields`): три честных
      состояния вместо двух — идёт цикл (знаем точно, свежесть визита не
      важна), «ещё ни разу не запускалась» (`last_cycle_start` нет вовсе —
      единственное надёжное «простаивает»), и «нет свежих данных» (цикл
      по расчёту кончился, но дальше неизвестно — не подставляется
      «простаивает»). `isColonyIdle()` для переработки задействует только
      первое надёжное состояние, поэтому теперь редко засчитывает
      колонию простаивающей — это не баг, а честность: для большинства
      колоний мы действительно не знаем текущее состояние фабрик.
      **Пересмотрено в тот же день.** Пользователь показал скриншот RIFT
      (сторонний intel-инструмент) с работающими фабриками, снятый БЕЗ
      захода в игру — и данные подтверждённо актуальны. Оказалось: факт
      про ESI («пересчитывает только при визите в клиент») верен, но
      вывод «дальше неизвестно» был излишне консервативным — так у
      сообщества PI-инструментов не принято. Planets in Space (ещё один
      сторонний трекер) прямо описывает в своём чейнджлоге: «Between ESI
      updates the app simulates your colony forward so the storage bars
      stay current» — досчитывает состояние вперёд локально от
      последнего подтверждённого снимка, предполагая, что фабрика
      продолжает крутиться сама (так она и ведёт себя в игре, пока есть
      сырьё). Это не выдумка в смысле правила 1 — настоящие
      `last_cycle_start`/`cycle_minutes` от ESI, честная проекция, а не
      случайное число.
      `pinCycleInfo()` переписана: вместо «нет свежих данных» после
      первого известного цикла — прогресс по модулю `(now -
      last_cycle_start) % cycle_minutes`, с пометкой `projected` для
      панели («проекция: колонию давно не открывали в игре»). Кольцо на
      круге теперь крутится дугой и во время подтверждённого, и во время
      спроецированного цикла — мигает только у пина, где
      `last_cycle_start` нет вовсе (`idle` — реально ни разу не
      запускалась, единственное состояние, для которого проецировать
      нечего). Тот же вопрос остаётся открытым для заполненности
      причала/склада (`contents`) — по тем же источникам, скорее всего,
      подвержена той же особенности ESI; решение по ней пока не принято.

      с уточнением области действия (11.09.2026).** Изначально в этом же
      пункте было записано «связать просадку с производственной цепочкой

      только если персонажи уже что-то производят — либо цепочка была при

      будет — предупреждать о его цепочке значило бы предполагать
      действие, которого пользователь не совершал.

      совпадение есть — предупреждение называет продукт цепочки под угрозой
      и предлагает добавить добывающую колонию (`extrDeficitChain`, RU/EN);
      если нет — остаётся прежний общий текст «дефицит — нужна
      дополнительная добыча» (`extrDeficit`), без ложного утверждения о
      конкретной цепочке, которой на самом деле нет. Без точного расчёта
      «сколько именно персонажей/планет не хватает» — по решению
      пользователя: «просто добавьте ещё одну добывающую колонию», без
      непроверенной арифметики (см. правило 1: не было честного источника
      для понятия «скорость добычи здоровой колонии», кроме самого порога
      48 000 ед./ч).
