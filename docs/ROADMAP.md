## 2. Что сделано

### Фаза 1 — Фундамент
- Данные проверены и сверены: рецепты P0–P4 (68 продуктов, ноль расхождений с вики),
  шаблоны застройки (68 игровых JSON, только вариант 00), `type_ids.json`.
- `domain/capacity.py` — CPU/PG: структуры + головы экстракторов + линки по радиусу против лимита CC.
- `domain/templates.py`, `throughput.py`, `factory_site.py`, `planner.py` — разбор шаблонов,
  пропускная способность, подбор планет (только Barren/Temperate, по возрастанию радиуса),
  распределение персонажей с честным дефицитом.
- Flask-слой отдаёт `web/` с того же origin (CORS не нужен); `scripts/diagnose.py` — самодиагностика.
- Убраны выдуманные данные (`Math.random()` вместо таймеров), удалён несуществующий `Positron Cord`.
- Экспорт в Excel (План / Сводка / Проверка).

### Фаза 2 — Фоновые сборщики
- `scripts/esi_client.py` — единая точка обращений к ESI: User-Agent, ETag/Expires,
  обе независимые квоты, самоторможение по лимиту ошибок (`docs/ESI.md`).
- `refresh_market_prices` (цены по расписанию), `refresh_tokens`, `scheduler.py` одним процессом
  с журналом. Пользователь никогда не запускает обращения к ESI (правило 3).

### Фаза 3 — ESI SSO и синхронизация
- Слой БД (SQLAlchemy 2.0 + Alembic), шифрование токенов (Fernet), таблица `credentials`.
- OAuth PKCE (`api/blueprints/auth.py` + `esi_sso.py`), первая синхронизация после входа в фоне,
  отзыв токенов на нашем сайте, «основной + альты» как постоянная группа.
- Сборщики `sync_character_skills` (6 ч) и `sync_colony_status` (30 мин); блок «Мои колонии в игре»,
  настоящие таймеры экстракторов, состав и загрузка структур реальной колонии.
- Изоляция данных между пользователями (`account_id`, `api/session.py`).

### Фаза 4 — Функциональное расширение
- Прямое R0→P2 (`domain/direct_p2.py`) — код есть, в интерфейсе выключен (см. 3.2).
- Предупреждение об истечении программ экстракторов; настоящая загрузка CPU/PG, входы и прогресс цикла фабрик.
- Мультирегиональность поддержана кодом (колонка `Region` в справочнике).

### Фаза 5 — Frontend и UX
- Интерфейс RU/EN доведён до конца (`T`, `plan_messages.py`, `api/errors.py`).
- Дашборд плана: детали/список/сетка, панель колонии; статус фоновых сборщиков; справка и «О проекте».

### Фаза 6 — Развёртывание
- `serve.py` (waitress), журнал в файл, `backup.py` (SQLite / Postgres / MariaDB),

### 3.1 Мультирегиональность, фазы 4–5 — в очереди
- [ ] **Фаза 4.** Регион доступен в планировщике только в статусе `ready`; серверная валидация
  в `PlanRequest`: домашняя система — в том же регионе, что и добыча (при нескольких регионах — в одном

  (сейчас есть только для Fountain). 24 колонки «прямого P0→P2» для новых регионов не заполняются.

### 3.2 Прямое производство P0→P2 на одной планете
- [ ] Проверка в игре: код готов (`domain/direct_p2.py`), в интерфейсе выключен (`direct_p2 = False`
  в `api/blueprints/plans.py`), застройка посчитана из стоимостей структур, а не из проверенного шаблона.
  Нужно: включить флаг, построить план, реально застроить планету и сверить CPU/PG.

### 3.3 Проверка второго причала в игре
- [ ] Расхождение источника: `Starport ×2 = 5200` против 2×3600 = 7200 CPU. Пока действует консервативное 7200
  (`assumptions.launchpad_count_for_two_templates`). Нужна планета Barren/Temperate ≈ 20 000 км —
  в Fountain такой нет, отложено.

### 3.4 Оптимизация бэкапов при росте базы
- [ ] Сейчас `scripts/backup.py` снимает полную копию каждый раз. Когда база вырастет — инкрементальные
  варианты для каждой СУБД (SQLite / Postgres / MariaDB), карта вариантов — в `HISTORY.md`, Фаза 9.

## 5. Правила

Полный список — `CLAUDE.md`, «Правила проекта» (проверяется тестами). Кратко:

1. **Никаких выдуманных данных.** Нет значения — «нет данных».
2. **Источник при расхождении:** JSON-шаблоны застройки, затем сверка по всем источникам.
3. **Пользователь не инициирует обращения к ESI.** Всё внешнее — фоновые сборщики; исключение `/api/auth/*`.
4. **Flask, без Docker.** SQLAlchemy 2.0 + Alembic, прод — MariaDB, dev — SQLite.
5. **Не нагружать сервер:** кэши с ETag, расчёт вне блокировки, лимиты размера запроса.
6. **Справка и «О проекте»** обновляются вместе с кодом (`domain/features.py`, `tests/test_docs.py`).
7. **Версия только в `version.py`.**
8. **Вёрстка проверяется тестом** (`tests/test_frontend_integrity.py`).
9. **RU/EN:** каждая новая строка сразу переводима (`T`, `plan_messages.py`, `api/errors.py`).
10. **Документы правятся в том же заходе, что и код** (этот файл, `CLAUDE.md`, справка).
11. **ESI/SSO — по документации CCP** (`docs/ESI.md`); единственные точки — `esi_client.py`, `esi_sso.py`.

## 6. Как мы работаем

- Одна правка — одна ветка — один PR. Перед PR: `python -m pytest tests -q` и `ruff check .`
  (то же самое гоняет CI).
- Каждый PR: обновить этот файл (перенести пункт из «Осталось» в «Сделано»), `CLAUDE.md` при смене
  устройства, справку при смене поведения, поднять версию в `version.py`.
- Пункты плана реализуются только по явной команде пользователя. Если пользователь перечислил пункты —
  сначала записываем сюда, код не трогаем до слова «делай».
- PR сливается после слова пользователя «готово»; затем — деплой на VPS и проверка версии через `/api/meta`.
- Подробности «почему так решено» пишутся в `HISTORY.md` (запись в фазе 9 или 11), а здесь остаётся
  только итог одной строкой.
- Тесты пишутся на то, что уже ломалось; ошибки признаются и чинятся в том же заходе.
