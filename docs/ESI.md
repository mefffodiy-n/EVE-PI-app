# Работа с ESI и SSO

Вынесено из `CLAUDE.md` (16.09.2026, по образцу `docs/ESI.md` в
github.com/Alexmidrus/EveGAS_calc) — правило 11 оттуда, здесь развёрнуто
в отдельный документ, а не сокращено. `CLAUDE.md` держит короткую ссылку
сюда.

Строго по официальной документации CCP — источник истины:
<https://developers.eveonline.com/docs/> (разделы «Services and
Resources → ESI» и «→ SSO», дев-блог с changelog). Сверяться с ней перед
любой правкой сетевого слоя, а не по памяти — CCP меняет правила, и
нарушение лимитов ведёт к бану приложения.

## Единая точка обращения

**Единственная точка обращения к API EVE — `scripts/esi_client.py`.**
Никаких прямых запросов к `esi.evetech.net` или `login.eveonline.com` из
других модулей, и никогда из HTTP-обработчика (правило 3 в `CLAUDE.md` —
пользователь не инициирует обращения к ESI). Обоснование каждого
заголовка — в докстринге `esi_client.py`. Обращения к SSO (обмен кода,
отзыв) — через `scripts/esi_sso.py`.

## Заголовки запроса

- **`X-Compatibility-Date` зафиксирован константой**, а не «сегодня»: в
  этом весь смысл заголовка — «поведение, которое мы проверили».
  Поднимать только вручную, сверившись с changelog. CCP держит обратную
  совместимость минимум год.
- **`User-Agent` собирается из `version.py`** (имя, версия, контакт —
  правило 7 в `CLAUDE.md`). Для запросов из браузера —
  `X-User-Agent`/`user_agent`: Chrome вырезает стандартный заголовок.

## Два независимых лимита

ESI ограничивает по двум независимым системам (не одной) —
`developers.eveonline.com/docs/services/esi/rate-limiting/`:

1. **Старый лимит ошибок** — 100 ответов НЕ 2xx/3xx в минуту, ОБЩИЙ НА
   ВСЁ ПРИЛОЖЕНИЕ, не на пользователя. Читать
   `X-ESI-Error-Limit-Remain`/`-Reset`, останавливаться с запасом до нуля
   (`ERROR_LIMIT_FLOOR`) — ноль означает 420 на всех маршрутах. Это
   единственная защита, которая по конструкции одинаково работает что
   при одном пользователе, что при сотне: общий бюджет исчерпывается
   быстрее при массовом сбое, но клиент останавливает ВСЮ синхронизацию
   раньше, чем дойдёт до 420.
2. **Новая система** — плавающее окно ТОКЕНОВ на пару (группа маршрута,
   персонаж): 2 токена за 2xx, 1 за 3xx, 5 за 4xx, 0 за 5xx, заголовки
   `X-Ratelimit-Remaining/Limit/Used/Group`, `Retry-After` при 429.
   Бюджет считается НА ПЕРСОНАЖА — масштабируется сама по себе, сотня
   пользователей с личными персонажами не делит один бюджет. Защита —
   реактивная: `Retry-After` на 420/429 уважается, повтор не раньше.
   `X-Ratelimit-Remaining/Limit/Group` дополнительно читаются заранее
   (`EsiClient.token_limits`, `docs/ROADMAP.md`, Фаза 9, 16.09.2026) —
   ТОЛЬКО для наглядности в логе сборщика, не для самоблокировки: этот
   лимит не общий на приложение, реактивной защиты уже достаточно.

Уважать `Retry-After` на 420/429 в обоих случаях.

## Кэш

**`ETag`/`If-None-Match`** реализованы — 304 не ошибка и не трафик.
Документация также требует не запрашивать раньше `Expires` (это
считается обходом кэша так же прямо, как игнорирование `ETag`) — с
12.09.2026 `EsiClient` хранит `Expires` вместе с `ETag` и пропускает
запрос вообще, пока кэш не истёк (`_cache_fresh()`), а не только ставит
`If-None-Match` и ждёт честный 304. Подробности в `docs/ROADMAP.md`.

## SSO — вход и отзыв

**Вход** — OAuth2 Authorization Code + **PKCE** (`login-url`/`callback`),
без опоры на `client_secret` в самом flow. Приложение зарегистрировано
как confidential (владелец задал `PI_ESI_CLIENT_SECRET` в `.env` VPS, не
в git) — секрет используется ТОЛЬКО там, где документация прямо требует
его для конкретного действия (отзыв, ниже; опционально при обмене кода,
если задан, `esi_sso.py::_token_request`), сам вход остаётся PKCE без
изменений.

Access-token (JWT) проверяется по JWKS: issuer
`https://login.eveonline.com/`, audience содержит `client_id` и
`"EVE Online"`, срок не истёк. Refresh-токены шифруются at rest.
Запрашиваются только необходимые scope.

**Отзыв токена:** `POST /v2/oauth/revoke` (адрес — из
`.well-known/oauth-authorization-server`) принимает только
`client_secret_basic`/`_post`/`_jwt` — без секрета невозможен ни при
каких условиях, с секретом реализован (`scripts/esi_sso.py::revoke()`,
`client_secret_basic`). Кнопка «Отвязать»
(`api/blueprints/auth.py::unlink`) всегда стирает свою копию токена
(гарантировано), и дополнительно пытается настоящий отзыв на CCP, если
секрет задан — сбой обращения к CCP не мешает локальному удалению. Ответ
несёт `revoked: bool`, UI честно показывает, что произошло на самом деле.

## Исключение из правила 3

Правило 3 (`CLAUDE.md`) запрещает HTTP-обработчикам, отдающим ДАННЫЕ,
ходить в сеть. Исключение — `/api/auth/*`, и оно двойное:

1. Обмен OAuth-кода на токен — синхронный вызов к `login.eveonline.com`
   прямо в обработчике: без него колбэк не имеет смысла. Разовое
   действие пользователя, не обслуживание данных; на лимит ошибок
   ESI-API не влияет (это не он).
2. Первая синхронизация скиллов/колоний нового персонажа сразу после
   входа (`_sync_first_login_async` в `api/blueprints/auth.py`) — эти
   вызовы уже идут в `esi.evetech.net` и расходуют его лимит ошибок,
   поэтому вынесены в фоновый поток, не блокирующий HTTP-ответ. Не
   заставлять персонажа ждать ближайшего расписания `scheduler.py`
   (скиллы — 6 ч, колонии — 30 мин) — тоже разовое действие в ответ на
   вход, а не обслуживание данных по расписанию, и для этого персонажа
   ещё не было ни одного запроса, значит не может быть преждевременным
   повторным.

Дальше токены обновляет фоновый `refresh_tokens`, а не обработчик.
