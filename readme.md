# PI Director v2 — скелет проекта (Фаза 1)

Скелет структуры из `roadmap.md` для Фазы 1 — «Фундамент (без ESI вообще)».

## Правила проекта, зашитые в архитектуру

1. **Только проверенные источники.** Все числовые константы происходят из
   `recipes.json` (перенос из v1) и `data/pi_reference.json` (разбор
   DalShooth/EVE_PI_Templates). Ничего не додумано; спорные места
   помечены в `_source` и `assumptions`.
2. **Минимум обращений к ESI, и никогда — по действию пользователя.**
   HTTP-слой (`api/`) не содержит ни одного внешнего вызова. Всё, что
   требует сети, живёт в `workers/` и запускается по расписанию (Фазы 2–3).
3. **Flask, не FastAPI.**
4. **Никакого Docker.** Обычное WSGI-приложение за nginx.
5. **Не нагружать сервер при большом числе пользователей** — см. ниже.

## Запуск

```
pip install -r requirements.txt
python run.py                 # разработка, http://127.0.0.1:8000
```

Production (Docker не используется):
```
# Windows
waitress-serve --host=127.0.0.1 --port=8000 api:app
# Linux
gunicorn -w 4 -b 127.0.0.1:8000 api:app
```
Статику (`web/`) в production лучше отдавать через nginx напрямую,
минуя Python.

## Как снижается нагрузка

Flask синхронный: пока обработчик считает, воркер не обслуживает других.
Поэтому:

- **Справочники считаются один раз на процесс** (`lru_cache`) и отдаются
  с **ETag** — на повторный запрос сервер возвращает 304 и не формирует
  тело вообще. Это самый дешёвый уровень.
- **Расчёт плана кэшируется по параметрам** (`api/cache.py`): он
  детерминирован, а набор возможных комбинаций ограничен справочником.
  Расчёт идёт вне блокировки, чтобы один долгий запрос не блокировал
  остальных.
- **Жёсткие лимиты на размер запроса**: не больше 20 целевых продуктов
  на расчёт и 500 строк на экспорт — иначе один запрос занял бы воркер
  надолго.
- **Тяжёлые pandas-операции не повторяются**: CSV читается и очищается
  один раз.

Кэш живёт в памяти одного процесса — при нескольких воркерах каждый
прогревается сам. Это осознанный компромисс: он ничего не стоит и не
требует Redis. Выносить в Redis стоит только после того, как нагрузка
подтвердится измерением.

## Как использовать этот архив

1. Распакуйте поверх текущего репозитория `EVE-PI-app`.
2. Скопируйте `planet industry.csv` в `data/planet_industry.csv`
   (см. `data/README.md`).
3. Положите полный набор 00-шаблонов в `data/templates/`.
4. Сформируйте данные о производительности:
   `python -m scripts.extract_schematics --write`
   (числа берутся из ваших шаблонов, обращений к ESI нет).
5. Удалите из репозитория `__pycache__/`, `pi_director.db` и старый
   `miner_p1.json` — последний содержит неверные числа.
6. `pip install -r requirements.txt`, затем `python run.py`

## Что реализовано и проверено

- **`domain/recipes.py`** — загрузка и валидация `recipes.json`.
  69 рецептов (8×P4, 22×P3, 24×P2, 15×P1), все входы разрешаются.
- **`domain/capacity.py`** — расчёт CPU/PG: структуры шаблона + головы
  экстракторов + линки (по формуле от радиуса) против лимита командного
  центра. Проверяет ограничения: два шаблона только при CCU V,
  P4 только на Barren/Temperate.
- **`domain/templates.py`** — разбор игровых JSON-шаблонов и подстановка
  `CmdCtrLv` под уровень персонажа для выдачи файла в игру.
  Варианты LS пропускаются (решение проекта — только 00).
- **`domain/factory_site.py`** — подбор планет под переработку: только
  Barren/Temperate, по возрастанию радиуса, с предупреждением и выбором
  вместо тихого отката на одиночный шаблон.
- **`domain/planets.py`** — загрузка CSV, нормализация заголовков и
  радиуса (в исходнике разряды разделены пробелами — без очистки
  сравнения радиуса молча давали бы неверный результат).
- **`domain/throughput.py`** — производительность фабрик и разворот
  потребности до сырья. Количества берутся из схем, извлечённых из
  ваших же шаблонов; ничего не додумывается.
- **`domain/planner.py`** — распределение персонажей по планетам:
  переработка в домашней системе, добыча на планетах с нужным сырьём,
  подбор персонажа по требуемому для данной планеты уровню CCU,
  учёт слотов планет, честные сообщения о дефиците.
- **`api/`** — Flask-слой: те же маршруты, что вызывает существующий
  `web/index.html`, единый формат ошибок, ETag, лимиты, кэш.
  `/api/calculate` подключён к планировщику полностью.

**Проверено числами:** стоимости структур сходятся со всеми сводками
README источника; формула линков воспроизводит все 60 точек 5 таблиц;
справочник совпадает с разобранными шаблонами. Тесты: 30 в
`tests/`, прогнаны — проходят все, кроме одного намеренно падающего
(дубль `Positron Cord` в рецептах).

## Что не реализовано

- **`workers/`, `infra/db`** — появятся в Фазах 2–3 вместе с реальной
  ESI SSO и планировщиком.
- **Экспорт в Excel** — `api/blueprints/export.py` пока заглушка;
  логика v1 переносится почти дословно.
- **`data/type_ids.json`** — закрывается запуском
  `scripts/extract_schematics.py --write`, который строит карту
  имён и id из шаблонов.

## Открытые вопросы

- Стоимость второго причала: README источника даёт 3600 CPU за один и
  5200 за два, хотя 2×3600 = 7200. Взято консервативное значение.
  Решает, применим ли двойной P4-шаблон на планетах крупнее 9 600 км
  (иначе предел 61 700). Проверяется постановкой двух P4-шаблонов на
  планету ~20 000 км при CCU V.
- `Positron Cord` в `recipes.json` дублирует `Ukomi Superconductors`
  по входам, отсутствовал в `PI_TYPE_NAMES` v1, и шаблона для него автор
  не делал (45 шаблонов P2/P3 при 46 продуктах). Похоже, запись лишняя.
